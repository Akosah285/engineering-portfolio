<Explainer demoTitle="FSM Simulator">
  <Step>
    <p>
      Every traffic light, every microwave timer, every dishwasher cycle is
      built from the same small idea. There is a tiny brain inside that
      knows which mode it is currently in, and which buttons or signals are
      allowed to push it into a different mode. Press start on a microwave
      and it goes from idle to cooking. Open the door and it pauses. Press
      start again and it resumes. That decision-maker has a name — a
      finite-state machine — and once you have seen one, you start
      recognising them everywhere.
    </p>
  </Step>
  <Step>
    <p>
      This demo wraps a stopwatch — the same one from Lab 3. It has three
      modes it can be in: <em>stopped</em> (waiting for you),
      <em>ticking</em> (counting time up), and <em>paused</em> (frozen
      mid-count, remembering where it left off). The buttons it understands
      are start, pause, resume, reset, and a clock tick that fires every
      time the crystal oscillator pulses. That is the entire vocabulary of
      the machine — three states, five inputs, nothing else.
    </p>
  </Step>
  <Step>
    <p>
      Load the <strong>Start then pause</strong> preset and step through it
      by hand. The stopwatch begins in <em>stopped</em>. The first input is
      start — it moves to <em>ticking</em>. The next input is a clock tick
      — it stays in <em>ticking</em> (time is passing). Another tick —
      still <em>ticking</em>. The final input is pause — it moves to
      <em>paused</em>. Four button presses, and the machine landed exactly
      where you expected. That is the whole loop: read an input, look up
      the next mode, repeat.
    </p>
  </Step>
  <Step>
    <p>
      Here is the punchline that makes state machines worth their name.
      Press <strong>pause</strong> while the stopwatch is in
      <em>stopped</em> — nothing happens. Press <strong>resume</strong>
      while it is in <em>ticking</em> — nothing happens. The same button
      does different things depending on where the machine currently is.
      That is the difference between this and a calculator: the answer
      depends not only on what you just pressed, but on the history of
      everything you pressed before it, collapsed down into the current
      mode.
    </p>
  </Step>
  <Step>
    <p>
      That lookup rule has a name. Write it as
      <MathExpression latex="\delta(s, i) = s'" /> — given current state
      <em>s</em> and input <em>i</em>, the function δ returns the next
      state <em>s'</em>. For the stopwatch,
      <MathExpression latex="\delta(\text{stopped}, \text{start}) = \text{ticking}" />
      and
      <MathExpression latex="\delta(\text{ticking}, \text{pause}) = \text{paused}" />,
      and so on. Anything not in the table — like pressing pause from
      stopped — simply maps the state back to itself:
      <MathExpression latex="\delta(s, i) = s" />. A real FSM is just this
      table plus an initial state.
    </p>
  </Step>
  <Step>
    <p>
      The stopwatch is what is called a <em>Moore</em> machine: the only
      thing it shows to the outside world — the indicator light reading
      stopped, ticking, or paused — depends purely on which state it is
      in. The light only changes once the state has changed. The
      alternative, a <em>Mealy</em> machine, would let the output depend
      on the input as well, so a label could light the instant you press a
      button without waiting for the next clock edge. Moore behaviour is
      calmer and easier to time; Mealy is faster but jumpier.
    </p>
  </Step>
  <Step>
    <p>
      Three states means the machine needs
      <MathExpression latex="\lceil \log_2 3 \rceil = 2" /> bits to
      remember where it is — say <code>00</code> for stopped,
      <code>01</code> for ticking, <code>10</code> for paused. The fourth
      pattern <code>11</code> is unused, which is a free defensive
      feature: if a glitch or a bad reset ever flips the register into
      <code>11</code>, you can route that case straight to a fallback
      transition back to stopped. Two flip-flops, three legal states, and
      one paranoid spare.
    </p>
  </Step>
  <Step>
    <p>
      Reset is the one input that ignores everything else. From
      <em>stopped</em>, from <em>ticking</em>, from <em>paused</em> —
      pressing reset always sends the machine back to <em>stopped</em>
      with the count cleared. Load the <strong>Reset from running</strong>
      preset to watch the stopwatch tick for a beat and then snap straight
      to idle. Most real digital systems wire a synchronous reset like
      this onto every register, so a single power-on pulse drops the
      entire chip into a known starting position before the first useful
      clock cycle.
    </p>
  </Step>
  <Step>
    <p>Try it yourself.</p>
    <TryThis>
      Load the <strong>Never started</strong> preset. The input sequence
      is just tick, tick, reset — clock pulses arriving before anyone has
      pressed start. Watch what happens: the stopwatch sits in
      <em>stopped</em> and ignores every tick. The clock is wired up and
      running, but the machine refuses to count until you tell it to.
      That is the difference between a clock and an enable; an FSM only
      reacts to the inputs that its current state actually listens for.
    </TryThis>
  </Step>
  <Step>
    <p>
      So a finite-state machine is just three things: a current mode, a
      table of <MathExpression latex="\delta(s, i) \to s'" /> arrows, and
      a rule for what to output once you land. The <strong>Stopwatch FSM
      animation</strong> demo further down the page paints those same
      transitions onto a circle-and-arrow diagram and lets you walk the
      clock yourself; the featured problem on the <em>1011 sequence
      detector</em> builds on the same machinery to recognise patterns in
      a bitstream, and shows how a Mealy encoding can shave a flip-flop
      off the design. Same algorithm, different jobs.
    </p>
  </Step>
</Explainer>

<FeaturedProblem
  kind="Featured Solution"
  title="Karnaugh-map minimisation of a 4-variable Boolean function"
  attribution="Adapted from Dartmouth ENGS 31, SP20."
>
  <p>
    Minimise the sum-of-products form of
    <MathExpression latex="F(A,B,C,D)" /> where the function is
    1 for the canonical "majority-of-three-inputs" pattern across
    <MathExpression latex="\{A,B,C\}" /> with <MathExpression latex="D" />
    acting as an enable: <MathExpression latex="F = D \cdot \mathrm{Maj}(A,B,C)" />.
  </p>
  <p>
    The truth table has eight 1-cells where exactly two or three of
    <MathExpression latex="A,B,C" /> are high <em>and</em>
    <MathExpression latex="D=1" />. Arrange on a 4-variable K-map (rows
    in <MathExpression latex="AB" /> Gray order, columns in
    <MathExpression latex="CD" /> Gray order). The 1-cells form three
    overlapping pairs of adjacent squares — each pair eliminates one
    variable:
  </p>
  <MathExpression
    latex="F = ABD + ACD + BCD"
    display={true}
  />
  <p>
    Three prime implicants, each a product of three literals, total
    nine literals. Checking essentialness: cell
    <MathExpression latex="ABCD" /> is covered by all three implicants
    so contributes no constraint; cells
    <MathExpression latex="ABC'D" />,
    <MathExpression latex="AB'CD" />,
    <MathExpression latex="A'BCD" />
    are each covered by exactly one of the three implicants — so all
    three are essential.
  </p>
  <p>
    The cost of <em>not</em> minimising: the canonical sum-of-minterms
    form has 8 terms × 4 literals = 32 literals, ≈ 32 transistors per
    NAND-implementation of each AND gate. K-map minimisation gives 9
    literals — a roughly 3.5× reduction in gate count for an identical
    function. The K-map minimiser demo above runs this same algorithm
    interactively; the gain extends to dozens-of-input designs where
    hand minimisation breaks down and Quine–McCluskey or Espresso
    takes over.
  </p>
</FeaturedProblem>

<FeaturedProblem
  kind="Featured Solution"
  title="Sequence detector for '1011' — Moore vs. Mealy state count"
  attribution="Adapted from Dartmouth ENGS 31, SP20."
>
  <p>
    Design a finite-state machine that asserts its output on every
    occurrence of the bit pattern <code>1011</code> in a serial input
    stream (overlapping matches allowed). Compare the Moore and Mealy
    implementations on state count and timing.
  </p>
  <p>
    The natural Moore machine tracks "how much of <code>1011</code>
    have we matched so far?" with five states:
    <MathExpression latex="S_0" /> (no match),
    <MathExpression latex="S_1" /> (matched <code>1</code>),
    <MathExpression latex="S_2" /> (matched <code>10</code>),
    <MathExpression latex="S_3" /> (matched <code>101</code>),
    <MathExpression latex="S_4" /> (matched <code>1011</code>, output
    high). Transitions handle overlap: from
    <MathExpression latex="S_4" /> on input <code>1</code> jump back
    to <MathExpression latex="S_1" /> (the trailing <code>1</code>
    becomes the start of a new match); on input <code>0</code> drop
    to <MathExpression latex="S_2" /> via reusing the
    <code>1</code> at position 3. State register width:
    <MathExpression latex="\lceil \log_2 5 \rceil = 3" /> bits.
  </p>
  <p>
    The Mealy version collapses the output-only state
    <MathExpression latex="S_4" /> into a labelled transition. Four
    states (<MathExpression latex="S_0, S_1, S_2, S_3" />), with the
    output asserted on the transition
    <MathExpression latex="S_3 \xrightarrow{1/1} S_1" />. State
    register: 2 bits. The output now depends combinationally on the
    current input, which means it appears one clock cycle earlier than
    in the Moore machine — but it inherits any glitches on the input.
  </p>
  <MathExpression
    latex="\text{States: Moore} = 5, \quad \text{Mealy} = 4 \quad\Rightarrow\quad \Delta\,\text{FFs} = 1"
    display={true}
  />
  <p>
    The textbook trade-off in one example. Moore costs an extra flip
    flop but guarantees glitch-free, register-aligned outputs; Mealy
    saves the flop and gives faster response at the price of
    combinational outputs that need careful timing closure. The FSM
    simulator above lets you toggle between the two encodings on this
    exact problem; on a real datapath you pick Moore when the output
    drives another sequential block, Mealy when latency dominates.
  </p>
</FeaturedProblem>

<FeaturedProblem
  kind="Featured Solution"
  title="Why two flip-flops in series tame metastability"
  attribution="Adapted from Dartmouth ENGS 31, SP20."
>
  <p>
    Sampling an asynchronous signal — a button press, a UART receive
    line, anything not clocked by your FPGA — can drive a flip-flop
    into a metastable state where its output sits between the legal
    logic levels for a random duration before resolving. A single
    flop has unacceptable mean time between failures (MTBF) in most
    designs; cascading two flops fixes it.
  </p>
  <p>
    Let <MathExpression latex="T_w" /> be the metastability capture
    window (a few picoseconds, set by setup/hold geometry),
    <MathExpression latex="f_c" /> the clock frequency,
    <MathExpression latex="f_d" /> the data toggle rate, and
    <MathExpression latex="\tau" /> the flop's resolution time
    constant (exponential decay of the metastable amplitude). With
    <MathExpression latex="T_r" /> seconds available between the
    sampling clock edge and the downstream block reading the output,
    the probability that a single flop remains metastable past
    <MathExpression latex="T_r" /> is
  </p>
  <MathExpression
    latex="P_1 = T_w\, f_d\, f_c\, e^{-T_r / \tau},\qquad \mathrm{MTBF}_1 = \frac{1}{P_1\, f_c}"
    display={true}
  />
  <p>
    A two-flop synchroniser routes the first flop's output into a
    second flop clocked on the next edge; the second flop only sees a
    metastable input if the first flop failed to settle within one
    clock period. Treating the two events as approximately
    independent, the available settling time effectively doubles to
    <MathExpression latex="T_r + T_c" /> where
    <MathExpression latex="T_c = 1 / f_c" />:
  </p>
  <MathExpression
    latex="\frac{\mathrm{MTBF}_2}{\mathrm{MTBF}_1} \approx e^{T_c / \tau}"
    display={true}
  />
  <p>
    For a flop with
    <MathExpression latex="\tau \approx 30\,\mathrm{ps}" /> on a
    100 MHz clock (<MathExpression latex="T_c = 10\,\mathrm{ns}" />),
    the ratio is
    <MathExpression latex="e^{10\,\mathrm{ns} / 30\,\mathrm{ps}} = e^{333}" />
    — astronomically large. That's why the SCI Receiver in the
    Morse-code final project used a double-flop synchroniser on the
    raw Rx pin before feeding the FSM; a single flop would have
    statistically failed within minutes at 9600 baud. The
    FSM-stopwatch animation above is the deterministic side of
    sequential logic; the synchroniser is the quietly heroic part
    that keeps the asynchronous world from contaminating it.
  </p>
</FeaturedProblem>
